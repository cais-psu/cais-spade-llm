# Phase 5 validation and revision

Composition produces a **validated program proposal within its recorded validation scope**. New runs use `gazebo_pick_place_observed_geometry_direct_cartesian`: measured object bounds and support surfaces, grounded calculations, direct motion, collision checks and link-attacher custody. This scope requires neither unique CAD orientation, physical gripper fit, manufacturing tolerances nor precise seating. Saved `gazebo_pick_place_direct_cartesian` and assembly-validation runs retain their original geometry requirements. The separate **Run in Gazebo** action executes that exact program after fresh checks and requires motion, gripper and link-attacher acknowledgments. Composition executes no robot commands; completed commands do not establish physical assembly success. The original Phase 4 completion and saved programs remain immutable. See [implementation status](IMPLEMENTATION_PLAN.md) and [research evaluation](COMPOSITION_EVALUATION.md).

The owned [validation profile](config/phase5_validation.json) selects `validation_scope`. [Scope handling](agents/ra/validation_scope.py) rejects unknown values and interprets historical records without that field as `rigid_vertical_gear_assembly_direct_cartesian`. Those saved runs retain their assembly checks. Authoring requests and prompts, PA requests, validation reports and execution requests carry the same scope; execution rejects a different scope in fresh validation. Changing the default cannot authorize a previously failed program.

## One composition process

```text
Compose Primitive Program
→ RA authors and immediately displays a candidate
→ inspect its selected dependencies and missing inputs
→ capture measured robot context through the selected RA adapter
→ calculate selected helpers and validate the ordered program
→ PA receives missing/rejected product inputs and its validation findings together
→ PA investigates those needs and any RA-authored supplemental requests
→ RA explicitly binds supplemental evidence or changes its program; repeat checks, or stop
```

`agents/ra/refinement.py` owns this flow. `primitive_composition.py` records each exact RA submission, including rejected responses; a validator never inserts, removes or repairs steps. New independent runs start from completion and captured context. Only revisions inside the same pinned run receive that run's previous candidate, accepted supplemental evidence and findings. Historical drafts and programs do not become initial inputs.

The composition projection retains partial formal contracts: grasp/release expose only `held_part`; `model_name` is absent. Primitive descriptions and helper outputs supply domain knowledge without prescribing an execution order. The shared runtime signatures, robot actions and recovery sequences retain their existing behavior.

`agents/ra/validation_scope.py` supplies the single supported primitive set for all recorded scopes: `compute_pick_targets`, `compute_place_targets`, `move_cartesian`, `grasp_part`, and `release_part`. New authoring prompts and response schemas restrict selectable primitives to that set intersected with the selected robot's catalog. The full catalog and its nested contracts remain available as runtime reference. Unsupported submissions are recorded as invalid before PA investigation or robot capture; the host never removes or replaces a submitted step. RA chooses the order, repetitions and bindings of supported primitives. Historical proposals remain readable against their original catalogs, but an unsupported historical primitive fails validation before geometry checks and cannot execute.

## Evidence and dependencies

`program_dependencies.py` follows RA-selected `value_ref` and `result_ref` dependencies. It reports missing fields, incompatible bindings, deferred outputs and downstream dependencies without changing the program. Required nested fields are enumerated even when their containing geometry object is absent. Historical scope contracts retain the strict calculators' placement requirements, including `target_reference.target_point` and `target_origin_pose.x/y/z`; captured runtime signatures and controller fallbacks remain unchanged.

Missing, incompatible and unverified product measurements in the selected `product_geometry`, `target_pose` and `detected_parts` inputs reach PA with their exact step, parameter path, quantity schema, reason and selected evidence references. A populated but rejected height binding therefore reaches PA alongside empty inputs. Robot/control findings remain with RA. PA-owned validation failures also enter that same investigation; program-level findings use `step_index: null` and name the validator's check as their quantity. The recorded scope determines which validation roles are required. PA chooses measurements and tools, while RA alone corrects bindings.

RA may add `request_context` entries for supplemental facts using `step_index`, `quantity`, `authority` and `reason`. PA entries retain their wording and order, with the first request for each exact step/quantity kept when duplicated. A request for the same step, primitive, selected parameters and quantity is not repeated with unchanged product evidence, including evidence just returned by that investigation. Program-level requests similarly include the selected program and original finding in their duplicate check. Changed RA bindings can therefore request measurements against the newly selected inputs. The host supplies no replacement binding or task sequence.

`agents/pa/primitive_context.py` adds a bounded investigation after completion. It reuses approved retrieval/document/CAD/RGB-D/calibration producers. Supplemental native retrieval validates typed records and writes separate audits; it never merges ontology deltas, replaces ProductContextView, or repeats resource allocation. PA chooses its evidence tools and feature associations for the requested facts. Returned records and unresolved reasons go back to RA for its next decision. Simulation validation requires `part` and `scene` roles; its `goal` and `specification` response fields remain null. The historical assembly scope requires all four roles. These requirements do not prescribe an extraction sequence. Selected primitive inputs still require their own measurements, including placement geometry where a selected calculator needs it. Conflicting identity or changed goal requires the existing PA authority gate.

PA's evidence catalog includes hash-verified discovery metadata for already issued records, including partial evidence from earlier batches. PA reviews requests derived from RA-selected contracts and RA-authored supplemental requests, reuses applicable records, and may investigate other needs when one measurement is blocked. Its unresolved feedback retains requested quantities and step references and distinguishes uninvestigated requests from attempted measurements that remain ambiguous or unavailable. PA still chooses tools, their order, and when to finish; an ambiguous measurement does not trigger an automatic retry. In the observed-geometry scope, finish accounts for each requested quantity as provided (with a selected record and pointer), blocked (with a specific prerequisite), or not_investigated. One early finish with unresolved needs and remaining operations returns the actual operation count, including when PA labels an absent derived record or an incorrectly exhausted budget as blocked. PA selects the next action and can confirm a specific unavailable source prerequisite without spending every operation; the public response derives its unresolved messages from those outcomes.

The supplemental geometry tool catalog describes each tool's required records, outputs, units and limitations. PA can discover measured support planes in segmentation records, select `observed_surface`, and use `pick_geometry` to derive `product_geometry.board_center.z` from accepted object and support evidence. `assembly_geometry` derives placement inputs from PA-selected mating features. An absent derived record does not establish that source measurements are unavailable: PA considers supported measurement operations and reports a specific missing prerequisite when it cannot attempt one. These contracts prescribe no tool order and do not authorize the host to fill RA bindings or invent tolerances.

PA may instead select `surface_height(surface_ref, location_ref)` to evaluate an accepted observed plane at an issued calibrated world location. It derives only `product_geometry.board_center.z`; a unique CAD-origin pose is not needed for this scalar measurement. The result retains the plane, evaluation point, measurement timestamps and source pins, and remains `AssemblySurfaceEvidence`, so it cannot supply the required full part geometry. Binding a raw plane coefficient directly as support height is rejected: `offset_m` is a plane-equation coefficient, not generally a world Z coordinate.

The supplemental `observation_catalog` lists every issued view's opaque handle, measured support plane, candidate handles and compatible issued calibrations. Compatibility checks the observation frame, world target and source depth timestamp. `read_observation(segmentation_ref, observation_handle, field_path)` reads exactly the selected view without camera-index enumeration; it consumes one operation, including unsuccessful reads, and retains the 12,000-character value limit. `observed_surface` reports compatible issued references when PA supplies an incompatible calibration. An empty compatible list does not establish that approved calibration is unavailable: PA may explicitly request `surface_calibration`. The host neither selects a view's task role nor calls measurement tools automatically.

PA-facing observation/calibration reads, discovery metadata and errors omit internal camera names and positions; canonical evidence stays unchanged. Existing `read_record` rejects camera-position requests and retains issued opaque candidate-pointer reads. Observation lists use opaque-handle order. These controls remove particular presentation cues; they do not establish that the model is unbiased or that an observation supplies sufficient assembly evidence.

`tools/assembly_geometry.py` measures neutral CAD planar/circular features, oriented dimensions and observed support-plane candidates. PA binds selected measured instances/features to the exact accepted assembly relationship. Final part origin is derived from selected opposing seating planes and mating axes, independently of RA's candidate. The visible shaft centre alone is insufficient. An ambiguous pose does not establish an orientation or final pose. For the same observed candidate and approved calibration, `inspect_features` may return `part_height_m` as the world-vertical CAD extent from the already highest-ranked qualified pose hypothesis. It also measures every qualified hypothesis, retaining the individual heights and their range under `uncertainty`. This estimate uses no height-agreement threshold or averaging. Its source, registration metadata and warning remain recorded; the record stays ambiguous. Only the selected height scalar may use this partial record, never a full pose, support height or complete `part`/`goal`/`scene` evidence. The estimates do not establish sensor accuracy, and a raw CAD-local Z dimension is still insufficient.

Records retain units, coordinate frame, semantic reference point, observation time, uncertainty and source hashes. Derived source chains and mesh bytes are rechecked. Historical scene coverage requires every candidate in the selected segmentation records to have registered geometry, plus measured support planes. Observed-box scenes require every candidate in each declared observation, plus measured support patches; missing candidates are recorded and observations are never silently fused. Missing coverage stays unknown. Unobserved space and contact mechanics are explicitly outside this model; cross-camera identity fusion is not invented.

Missing calculator inputs remain distinct from physical-validation requirements: scene coverage supports collision checks, while the specification supplies acceptance criteria. Live and restored UI feedback shows current calculation/input failures before older PA explanations and secondary warnings; all findings and PA reasons remain in the trace. A failed pure calculation leaves independent subsequent calculations available; an unvalidated movement or custody transition still blocks later state-dependent checks. Missing evidence cannot pass validation or authorize execution.

A CAD file origin is a coordinate reference and can lie outside the physical part. PA may select `select_grasp_point(part_ref, plane_id, circle_id)` to bind a measured circular feature as the grasp reference. The returned part retains its original CAD-origin pose and collision mesh; `grasp_reference` records the selected point in CAD-local and world metres. `pick_geometry` uses that point and rejects a reference outside the measured part bounds. Grasp validation compares the TCP with the selected physical reference while carried-part and scene transforms continue to use the original CAD frame. The producer does not choose a feature or resolve an ambiguous pose.

When deriving mating geometry from that selected part, `assembly_geometry` retains the final CAD origin and supplies `product_geometry.grasp_point_offset_world_m` with `target_reference.grasp_point = selected_CAD_feature`. The placement calculation applies that measured vector before converting the TCP target to the controlled-link target. It cannot substitute zero when the selected feature offset is absent. The composition schema declares this conditional input through `x-grounding-when`; binding diagnostics resolve only RA-selected references and route the missing vector to PA. Existing CAD-origin programs keep their recorded catalog and arithmetic. Regression coverage translates the CAD coordinate origin while holding the physical object fixed, and requires unchanged pick/place targets, full validation, and fake execution.

These repairs support composition from available information within the existing primitive and validation scope. They add no USB cable, rgb cable or hex nuts controllers or evaluators. Broader composition experiments require the corresponding available capabilities; evaluate composition changes separately from measurement availability, with equal evidence and tools across comparison methods.

Only the assembly-validation scope requires assembly tolerances. They come from exact unit-bearing approved document spans selected by PA, or an explicit experiment specification. To supply the latter, set `validation_specification_path` in [the profile](config/phase5_validation.json) to a JSON file under `cases/`. It must be an accepted `AssemblyValidationSpecification` with `family: vertical_gear_assembly`, positive `position_tolerance_m` and `axis_tolerance_rad`, and an explicit `yaw_required` policy; yaw-required cases also need `orientation_tolerance_rad`. Declare `requires_threading` and `requires_force_control` honestly. The host snapshots and hashes the selected specification in that scope. Gazebo pick-and-place does not load or require it, and supplies no invented tolerance values.

## Observed geometry for link-attacher pick-and-place

`observed_geometry(segmentation_ref, observation_handle, calibration_ref)` measures all segmented candidate bounds in the PA-selected calibrated view. Visible world points extend to that view's measured support plane, an explicit approximation for occluded bottoms. Records retain world-aligned collision boxes, their `observed_bounds_center` reference poses, vertical extents, support Z, observed top points, uncertainty and pinned RGB-D/calibration sources. Box axes do not establish CAD orientation. The finite support patch covers the measured plane inliers within three recorded RMS residuals (with a numerical floor of one micrometre); unobserved surfaces remain unmodeled.

PA may select `bind_observed_part` to associate a measured candidate and approved CAD with an already accepted feature. This checks identity without requiring CAD registration. PA chooses the destination point and the records passed to `scene_geometry`. These tools prescribe no investigation order. RA receives selected measurement values and exact references in its revision context and alone updates `primitive_steps`. Already-resolved measurements still require their `value_ref` bindings; copying the displayed numbers into numerical geometry loses the source provenance. Reuse avoids unnecessary reads, not the evidence requirement.

The observed scope retains pick height, clearance, travel-height and measured EE–TCP arithmetic. Its placement input is `product_geometry.placement_surface_point` in world metres. Desired part-reference Z is surface Z plus half the measured part height plus the existing placement gap; the pick grasp-to-reference offset and measured EE–TCP transform then give the controlled-link target. `slot_xy`, shaft seating geometry and `target_origin_pose` are not required. Validation and execution invoke the same scoped calculator, and calculation fingerprints include the scope.

Validation carries and releases the selected box through the predicted tool-to-object transform. Part identity, TCP proximity and custody replace physical jaw-width/CAD-grasp tests. Only the selected part's contact with configured gripper touch links is allowed; arm, other-object and support collisions remain checked. After composition, execution matches the accepted CAD against live instance bounds and position using existing matching tolerances and requires exactly one match. Simulator information never supplies composition coordinates.

## Measured robot context and numerical calculation

`adapters/in_process_robot_agent.py` retains the exact-resource/lifecycle/readiness gate. `robot_validation_context.py` reads joint states, EE and TCP poses, their full relative transform, controller policy, tool links and URDF/SRDF/planning parameters through read-only ROS interfaces. Owned ROS contexts avoid changing another runtime's executor. Configuration names are not measured feedback. Default sensor age and capture skew limits are two seconds; scene age is 120 seconds, using ROS time for observations. Validation progress is persisted and displayed before robot capture. Wall-clock capture age is checked at validation entry, before asynchronous structure and evidence verification, so progress work and later verification do not expire an initially fresh snapshot. Missing timestamps, expired snapshots, inconsistent clocks, stale ROS samples and excessive capture skew have separate diagnostics. The owned measurement context stays alive while its snapshot enters validation. The entry timestamp is recorded before snapshot persistence, and teardown follows validation, so these delays cannot consume the entry allowance. Actual capture/sample timestamps and the two-second limit are preserved. The final measured capture and comparison remain required before a program can be accepted.

The approved shared extraction is `resources/robot/target_calculations.py`, used by the existing controller and the strict Spec2Primitives calculation adapter. The adapter evaluates only helper calls selected by RA, using resolved exact arguments and the predicted preceding EE pose. Its controlled-link target poses compensate the full measured EE–TCP translation at the selected orientation, including small horizontal components from measured tilt; scalar object and slot coordinates keep their original meaning. Placement preserves the predicted preceding orientation unless RA explicitly selects an existing grasp orientation. The owned validation and execution paths use this same calculator. It creates no controller/action clients, performs no detection or simulator lookup, and rejects missing dimensions, unresolved destination tokens, incompatible frames and invalid tool transforms instead of using runtime fallbacks.

Calculation records retain resolved arguments, actual extracted outputs, source hashes, robot policy/configuration hashes, preceding pose and cache key. Cache reuse requires matching inputs, sources and relevant robot context. The authored program remains separate from resolved values. `approach_pose`, `target_pose`, `pre_insert_pose`, and `insert_pose` remain distinct. Absent conditional outputs produce findings; reaching pre-insertion cannot satisfy a seated assembly requirement.

## Finite modeled validation

`agents/ra/program_validation.py` returns `passed`, `failed`, or `unknown` findings under the recorded scope. All scopes share evaluators for selected pick/place calculations, `move_cartesian`, and grasp/release custody. Capability checks precede geometry checks: an unsupported primitive is an RA-owned program error, not a request for PA measurements. Execution checks the same supported set. The table describes common checks and the additional historical assembly checks.

| Check | What is established within this model |
| --- | --- |
| Bindings | Supplied types/references, required calculation fields, actual conditional results, selected measurement provenance, units and frames. |
| Declared conditions/effects | Supported custody and pose transitions; unknown conditions/effects cannot silently pass. No planner searches these contracts. |
| Grasp | Observed scope: selected-part identity and proximity. Historical scopes: necessary TCP/part overlap and gripper-width envelope, followed by an explicit rigid part-to-tool assumption. This is not force closure, friction or gripper-contact validation. |
| Ordered motion | Complete collision-checked Cartesian segments from predicted prefix joints/pose, orientation, robot limits and carried mesh or observed box. |
| Release | Check carried-part identity and custody, then add the predicted released shape to the collision scene. The assembly scope additionally requires the specified seating relationship; support remains a nominal geometric assumption. |
| Outcome | Pick-and-place requires the complete selected program to pass and end with released custody. The assembly scope additionally checks final part-origin position and selected axis against approved tolerances, plus required orientation where declared. |

`adapters/isolated_moveit.py` starts a private worker with execution disabled and execution capabilities excluded. Its planning scene is separate from the live scene; robot start states and hypothetical carried/released geometry are supplied explicitly. Shared collision-object and joint-state inputs cannot mutate this frozen scene. Each authored movement must complete as one Cartesian segment. Controller fallback detours receive no credit as RA intermediate movements; runtime controller behavior remains unchanged.

Missing geometry, unavailable services, timeouts or incomplete paths cannot pass. A failed planning search is not proof that no feasible path exists. After a pass, another measured robot capture and source/scene-age checks can invalidate the result. Observation diagnostics distinguish missing timestamps, inconsistent ROS clocks and expired observations, including their measured age and configured limit. Deriving a new geometry record from the same RGB-D does not refresh its sensor timestamp; expired evidence needs current observations. Checks do not monitor the world indefinitely: the verdict is tied to the recorded snapshot and validity interval, not future execution authorization.

Robot contexts are saved before comparison, including the capture that causes rejection. The comparison checks the existing configuration/model hashes, frame and tool fields, `held_part`, EE/TCP transform, and all captured joint names and positions under the unchanged thresholds. Timestamp changes and joint-name ordering alone are not differences. Comparison events pin both captures and retain every differing field, its previous/current values, and applicable numerical differences and thresholds. A mismatch between refinement decisions still stops as `stale`; a mismatch after a provisional pass still produces an `unknown` `final_freshness` finding. Live and restored diagnostics use the same recorded comparison message, with full differences in the trace; reopening verifies the compared captures against their saved pins. A reported comparison difference does not by itself establish physical robot motion.

The shared [dual_moveit_gazebo.launch.py](../../ros2/cais_lab_robotics/launch/dual_moveit_gazebo.launch.py) leaves the MoveIt executable's node name unset in its `Node` declaration. The executable retains `/move_group`, while its helper retains `/moveit_simple_controller_manager`. Setting `name='move_group'` applied a global node-name remap to both, creating competing `/move_group/list_parameters` and `/move_group/get_parameters` services. Captures could therefore read different parameter sets and report `model_parameters_sha256` changes while the robot stayed stationary. The repair separates those services; parameter contents, comparison fields and thresholds remain unchanged.

After this launch-file change, run `make bootstrap-gazebo`, verify the installed launch file, and restart Dual Gazebo through its existing UI controls before composing again. Missing product, scene or specification evidence remains a separate validation gap. See the [recorded rollout and verification limit](IMPLEMENTATION_PLAN.md#robot-context-parameter-service-collision-2026-09-08): the service fixture passed, but the live retry reached its deadline before a second capture could test comparison across decisions.

## Budgets, persistence and UI

Defaults in the pinned profile are three candidate versions, two PA batches, twelve PA evidence operations total, a five-minute run deadline, 32 steps per candidate, and twelve individual RA evidence operations per authoring decision. Each PA batch receives at most six operations. Context-only RA decisions are also bounded by the candidate-plus-batch limit. Private-worker startup has a 30-second allowance; subsequent service/planning calls use 10/20-second limits; cancellation tears down the private worker before completing cleanup.

RA can select independent record reads in one `read_records` action with a `requests` list of exact `record_ref` and `field_path` pairs. The host returns ordered `results` through the same hash-checked reader used by `read_record`. Each requested item consumes one operation, including unavailable or oversized reads; `query_ontology` consumes one operation. An over-budget batch serves no items and stops with its reason recorded. The final decision after consuming the read budget can still propose or stop. Batched reads never prescribe evidence sources or alter `primitive_steps`.

Each composition input check validates PA completion once, passing that completion and its checked product view through assignment/snapshot validation and input construction. Full validation runs again before and after each model response; there is no cache across integrity checks or runs. A synchronous history check reuses already verified ancestor bytes while traversing every source chain; a later check starts with an empty verification map. Model-facing input and exchange JSON uses compact whitespace while retaining the complete catalog and evidence. Saved-record encoding, fingerprints and historical requests remain unchanged.

Runs stop on pass, repeated unchanged failures, unavailable/unsupported evidence, authority conflicts, stale context, exhausted budgets, cancellation or invalid submissions. Stop reasons and every first-pass/revised result remain recorded. A later Compose click starts a new run; no saved program is regenerated automatically.

`composition/refinement_runs/run_*/` contains the request/profile, events, measured contexts, PA requests/exchanges/evidence, candidate references, calculation/validation records and final result. Candidates retain their existing writer and per-request catalog. The UI shows the first proposal immediately, progress, the latest numbered program and short findings; earlier versions and traces expand. Validation findings belong to the exact pinned proposal checked. A newer proposal without a completed report shows validation pending, or that the run ended before validation completed; predecessor findings remain in the trace rather than appearing as failures of the revision. This association is preserved after reconnect. Worker checks remain outside the UI event loop, duplicate clicks join/exclude the active run, and reconnect reads the persisted progress.

RA input-check timings, model waits/response timings, prompt character counts and completed individual evidence requests emit `composing` events before a proposal exists. Model requests and evidence operations have separate counts, so one model request can complete several reads. The UI shows the current request count and elapsed time at the latest recorded update; these are activity records, not a continuously ticking timer or a promise of a response time. `Attempts` still counts submitted proposals, including after reconnect. Progress does not change the model, evidence budgets or run deadline.

PA emits model wait/response timings and tool start/completion events through the same persisted UI path. Events distinguish reads from measurement/geometry operations, retain outcomes and consumed budgets, and explicitly report when PA finished without attempting a measurement. PA's unresolved prose remains its assessment, not a measured fact. When PA's batch or operation allowance is exhausted, the next RA context states that no further PA investigation is available in that run.

The unchecked **Use 900 seconds for the next Compose run** option applies only to the next started composition and resets when the first saved progress event arrives. The owned `compose` API accepts a finite per-run `deadline_sec` override; each run snapshots its own profile, and joining an active run cannot change that profile. The UI displays the effective deadline from the saved run request separately from this checkbox, including after reconnect. Normal runs retain the configured 300 seconds. Every progress event remains persisted; ordinary model/tool updates refresh progress labels while expensive program and trace rendering waits for a proposal, validation result, PA response, robot-context comparison or run completion. Evidence budgets, sensor/scene freshness, cancellation, duplicate-click protection and execution gates are unchanged. A longer diagnostic run can expose later blockers; completion after 300 seconds is not evidence of meeting the normal deadline.

## Subsequent work and acceptance limits

### Run in Gazebo

`spec2primitives_ui.py` → `PrimitiveExecutionRuntime.run` → fresh `validate_program` → `GazeboExecutionSession` → immutable execution records.

The button runs the displayed saved program, with no new LLM call. It requires `validated_for_declared_scope`, the exact selected context-only RobotAgent, current catalog/configuration/evidence, the isolated Gazebo environment, and stopped hardware stacks. One application execution is allowed, with a filesystem lock excluding another application. Preparation revalidates the unchanged steps under their saved scope and retains complete timed Cartesian trajectories; the separate action client executes those trajectories while the private validation worker remains unable to execute. Helper results retain the strict calculation semantics. Grasp/release require gripper feedback and successful explicit link-attacher acknowledgments before custody changes; no recovery wrapper, movement detour or placement snap is used. New-scope UI messages are “Validated for Gazebo pick-and-place” and “Pick-and-place completed”; `assembly_success` remains null.

The execution-only CAD binding reads the configured installed Gazebo fixture/model definitions and verifies the accepted STL bytes. For example, the existing `gear_medium` model uses `Gear_Medium.STL`. Its SDF mesh scale and visual transform are applied before comparing the live instance pose with the accepted observed CAD pose. The matching thresholds are configured independently of assembly tolerances in [gazebo_execution.json](config/gazebo_execution.json): 10 mm position and 0.1 rad orientation. Exactly one match is required. Neither simulator names nor simulator state becomes recognition/composition evidence.

Execution artifacts append under `contexts/<interaction>/execution/run_*/`: the pinned request, preparation/validation, instance binding, step arguments/results, event chain, final result and optional final RGB-D capture. Reconnecting only reads these records. Stop cancels an active trajectory and waits for a terminal result; unavailable acknowledgments remain unknown. Unknown command/custody outcomes block later execution for both robots. Later context reads project only acknowledged `held_part` and `gripper_state`. A program whose commands were dispatched cannot be replayed; capture current context and compose a new program.

Read [the coordinator](agents/ra/program_execution.py), [the transport and CAD binding](adapters/gazebo_execution.py), [the read-only execution state](agents/ra/execution_state.py), and [the focused execution tests](tests/test_primitive_execution.py). UI regression coverage is in [test_pa_ui_connection.py](tests/test_pa_ui_connection.py). Existing saved programs and validation reports are preserved; old reports need fresh validation to obtain executable trajectory timing.

Hardware execution, force/contact validation, independently observed assembly success, continuous scene monitoring, broader geometry and threaded hex nuts remain subsequent work. Final RGB-D is captured for inspection without an automated success claim.

Controlled fixtures establish the dataflow, numerical parity and failure gates; they do not establish live LLM accuracy. A live no-motion pilot must report missing evidence and unavailable services as observed, separately from fixtures. Publication claims require the held-out comparisons, independent evaluation and outcome measurements in [COMPOSITION_EVALUATION.md](COMPOSITION_EVALUATION.md).
